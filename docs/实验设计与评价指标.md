# 实验设计与评价指标

## 三、实验设计与评价指标

### 3.1 实验目标

在完成算网共同碎片化量建模和碎片化收益驱动的动态通信优先级调度设计后，实验部分需要验证该方法是否真正改善了 AI 算力集群中的运行时碎片化转移。本文的实验目标并不局限于证明平均流完成时间下降，而是从资源形态、任务性能和网络行为三个层面验证方法有效性。

具体而言，实验需要回答以下问题：

1. 算网共同碎片化量是否比单纯 GPU 空闲率、完整主机数量等传统指标更能解释后续任务可调度性？
2. 基于碎片化收益的通信优先级调度是否能够降低运行时碎片化量，并提升完整高速互联 GPU 资源块数量？
3. 动态通信提权是否能够改变任务完成顺序和资源释放轨迹，从而改善后续任务调度空间？
4. 该机制在改善碎片化的同时，是否能够维持训练任务 JCT、推理任务 SLA 和网络队列稳定性？
5. 相比固定优先级、传统动态优先级、CRUX 风格方法和仅碎片化感知路由方法，本文方法的收益主要来自哪里？

因此，实验部分应围绕“碎片化量是否有效”“通信提权是否有效”“系统代价是否可控”三条主线展开。

### 3.2 对比方法

为了全面评估本文方法，实验中建议设置以下对比方法。

#### 3.2.1 Fixed Priority

Fixed Priority 表示固定优先级调度策略。该方法根据任务类型静态分配优先级，例如推理任务使用高优先级队列，训练任务使用低优先级队列。该基线用于说明静态业务类型优先级无法适应运行时任务状态、资源释放收益和碎片化量变化。

#### 3.2.2 FIFO / WRR

FIFO 或 WRR 表示基础网络队列调度策略。FIFO 按到达顺序调度流量，WRR 按固定权重轮询多个优先级队列。该基线用于提供不感知任务语义、不感知碎片化量的基础性能下界。

#### 3.2.3 Queue-aware Dynamic Priority

Queue-aware Dynamic Priority 表示仅根据网络队列状态进行动态优先级调整的方法。该方法可以使用队列长度、等待时延、CNP 采样或流完成时间估计作为优先级调整依据，但不考虑任务提前完成后的资源释放收益。该基线用于证明仅优化网络局部时延并不足以改善集群长期可调度性。

#### 3.2.4 CRUX-like

CRUX-like 表示基于 GPU 强度或任务占用 GPU 数量的优先级调度方法。占用 GPU 数量更多的任务获得更高通信优先级或更早路径选择权。该基线用于比较“任务规模”与“碎片化收益”作为调度信号的差异。本文预期表明，占用更多 GPU 的任务并不一定具有更高碎片化释放收益；相反，释放关键主机、关键 ToR 域或高质量资源块的任务才应获得短时提权。

#### 3.2.5 CASSINI-like

CASSINI-like 表示网络兼容性感知调度方法。该方法尽量错开共享链路任务的通信高峰，降低训练任务之间的链路竞争。该基线用于比较“降低网络竞争”与“改善碎片化转移”的差异。CASSINI-like 主要优化共享链路拥塞和训练 JCT，而本文方法进一步关注任务完成顺序对资源释放轨迹的影响。

#### 3.2.6 Frag-routing only

Frag-routing only 表示仅在路由选择侧使用碎片化量的方案。该方法根据算网共同碎片化量选择更有利于保留完整资源块的路径，但不在通信队列调度侧进行任务提权。该基线用于证明运行时队列优先级调整仍然有必要：即使路由选择已经考虑碎片化，任务完成顺序仍会受到通信调度影响。

#### 3.2.7 Proposed

Proposed 表示本文提出的碎片化收益驱动动态通信优先级调度方法。该方法综合考虑任务提前完成后的碎片化释放收益、预计剩余完成时间、推理 SLA 压力和网络干扰成本，并将任务级收益映射为流级、QP 级或包级优先级偏移。

#### 3.2.8 Oracle

Oracle 为可选上界方法。该方法假设系统已知未来任务到达、运行时间和资源需求，并选择全局最优的提权任务。Oracle 不作为实际可部署方法，而用于衡量本文在线算法与理论最优之间的差距。

若实验实现时间有限，建议至少包含 Fixed Priority、Queue-aware Dynamic Priority、CRUX-like、Frag-routing only 和 Proposed 五种方法。

### 3.3 工作负载设计

实验应覆盖训推混合负载，而不是仅测试训练流或单一类型流量。训练任务、推理任务和混合比例均需要进行系统设置。

#### 3.3.1 训练任务负载

训练任务可按照 GPU 数量、通信模式、通信强度和任务时长进行划分：

- GPU 数量：1、2、4、8、16、32；
- 通信模式：AllReduce、Parameter Server、Pipeline Parallel 通信；
- 通信强度：低通信强度、中通信强度、高通信强度；
- 任务时长：短任务、中任务、长任务。

其中，AllReduce 密集型任务适合用于验证算网共同碎片化量的必要性，因为这类任务对 GPU 间带宽和路径延迟高度敏感。

#### 3.3.2 推理任务负载

推理任务可按照请求到达过程、流大小、SLA 约束和外部 RTT 进行设置：

- 请求到达：Poisson 分布或长尾分布；
- 流大小：小流为主，包含少量中等规模流；
- SLA 约束：宽松、中等、严格三档；
- 外部 RTT：低、中、高三档，用于模拟数据中心外部网络状态对 QoE 的影响。

推理任务用于验证本文方法是否会因训练任务短时提权而破坏在线任务 SLA，也用于评估 SLA 压力项在动态优先级映射中的作用。

#### 3.3.3 训推混合比例

建议设置三类混合比例：

- 训练主导：80% training / 20% inference；
- 均衡混部：50% training / 50% inference；
- 推理主导：20% training / 80% inference。

通过改变混合比例，可以观察本文方法在不同业务压力下对训练 JCT、推理 SLA 和碎片化量的影响。

#### 3.3.4 碎片化场景构造

为了验证算网共同碎片化量的有效性，需要主动构造不同类型的初始碎片化状态：

- 同主机碎片：空闲 GPU 分散在多台 8-GPU 主机中，难以形成完整 8 卡主机；
- 同 ToR 碎片：空闲 GPU 分散在同一 ToR 下的不同主机中；
- 跨 ToR 碎片：空闲 GPU 分布在多个 ToR 域中，通信需要经过更高层级交换；
- 跨汇聚域碎片：空闲 GPU 跨越不同汇聚域或 Pod，通信路径更长且带宽竞争更强。

这些场景能够区分纯计算碎片化和算网共同碎片化，从而证明本文指标的表达能力。

### 3.4 拓扑与参数设置

基于 ns3-alibaba 调度模块，实验可以在不同集群规模和网络参数下进行扩展验证。建议考虑以下参数：

- 集群规模：128、256、512、1024 GPU；
- 主机规格：每台主机 8 GPU；
- 接入带宽：100G 或 200G；
- 汇聚带宽：400G 或 800G；
- oversubscription ratio：1:1、2:1、4:1；
- 优先级队列数量：4、6、8；
- 调度周期：100 us、500 us、1 ms、5 ms。

重点参数扫描可以围绕以下变量展开：

- 网络负载强度；
- 训推混合比例；
- 初始碎片化程度；
- 交换域带宽差异；
- 推理 SLA 紧迫程度；
- 任务大小分布；
- 动态提权阈值。

通过这些参数扫描，可以分析本文方法在不同拥塞程度、不同碎片化程度和不同业务压力下的稳定性。

### 3.5 评价指标

实验指标应分为三类：碎片化与可调度性指标、任务性能指标和网络性能指标。

### 3.5.1 碎片化与可调度性指标

碎片化与可调度性指标是本文最核心的评价维度。

#### 算网共同碎片化量

首先记录算网共同碎片化量的时间序列：

$$
F_{\text{cn}}(t)
$$

并进一步统计：

- 平均碎片化量；
- P95 碎片化量；
- 碎片化量时间积分 $\int F_{\text{cn}}(t)dt$；
- 任务完成后的 $\Delta F_{\text{cn}}$ 分布；
- 碎片化恢复时间。

其中，碎片化量时间积分用于刻画整个运行期间集群处于高碎片化状态的总体程度。碎片化恢复时间表示从高碎片化状态恢复到可接受阈值以下所需的时间。

#### 完整资源块数量

为了提供更直观的解释，还应统计：

- 完整 8-GPU 主机数量；
- 同 ToR 内可组成的 8-GPU 资源块数量；
- 满足带宽和延迟约束的 k-GPU 资源块数量；
- 高速互联 GPU 可用数量。

这些指标可以展示本文方法是否真正保留了更多高质量算网资源块。

#### 未来任务可调度成功率

未来任务可调度成功率定义为：在当前集群状态下，从未来任务需求分布中采样若干任务，统计其中能够找到满足 GPU 数量、带宽和延迟约束的放置方案的比例。

该指标可表示为：

$$
R_{sched}(t)=
\frac{1}{N}
\sum_{i=1}^{N}
\mathbb{I}(\text{Schedulable}(m_i,X_t))
$$

其中，$m_i$ 为从未来任务分布中采样的任务，$X_t$ 为当前集群状态。该指标比单纯完整主机数更能反映集群对未来工作负载的实际承载能力。

#### 碎片化导致的阻塞率

还可以统计因碎片化导致的新任务阻塞率，即集群中空闲 GPU 总数满足任务需求，但由于 GPU 分布、带宽不足或路径延迟过高而无法调度的任务比例。

该指标能够直接证明算网共同碎片化与传统 GPU 利用率之间的差异。

### 3.5.2 任务性能指标

任务性能指标用于评估本文方法是否在改善碎片化的同时保持训练和推理任务性能。

#### 训练任务指标

训练任务建议统计：

- 平均 JCT；
- P95 / P99 JCT；
- 平均 slowdown；
- AllReduce 完成时间；
- iteration time；
- 由网络等待导致的 GPU idle time。

其中，GPU idle time caused by network 是一个关键指标，用于说明网络调度是否减少了 GPU 因通信阻塞产生的空转。

#### 推理任务指标

推理任务建议统计：

- 平均响应时延；
- P95 / P99 响应时延；
- TTFT；
- SLA violation ratio；
- 不同外部 RTT 条件下的 SLA 保持率。

这些指标用于验证本文方法在对部分训练任务短时提权时，是否仍能控制在线推理任务的服务质量。

#### 混合负载总体指标

在训推混合场景下，还应统计：

- 系统吞吐；
- 单位时间完成任务数；
- 任务平均排队时间；
- 任务完成顺序变化；
- 不同任务类型的性能公平性。

其中，任务完成顺序变化可以用于直接说明本文方法确实通过通信调度改变了资源释放轨迹。

### 3.5.3 网络性能指标

网络性能指标用于证明动态提权没有破坏网络稳定性，也没有粗暴占用高优先级队列。

建议统计：

- 平均 FCT；
- P95 / P99 FCT；
- coflow completion time；
- 各优先级队列平均等待时间；
- 各优先级队列 P95 等待时间；
- 高优先级队列占用率；
- 链路利用率；
- 瓶颈链路利用率；
- ECN / CNP 数量；
- 队列长度分布；
- 丢包或重传数量，如果仿真器支持。

尤其需要关注高优先级队列占用率和队列等待时延分布。若本文方法的高优先级占用率明显过高，说明短时提权可能退化为长期高优先级占用；若占用率可控且碎片化量下降，则说明提权策略具有较好的系统收益。

### 3.6 消融实验

为了证明本文方法中各个设计项的必要性，需要进行消融实验。

#### 3.6.1 w/o Frag Gain

去掉碎片化释放收益，仅根据队列状态或任务类型调整优先级。该实验用于证明碎片化收益信号本身对改善资源状态具有贡献。

#### 3.6.2 w/o Remaining Time

去掉剩余完成时间归一化，即不使用单位通信代价收益 $E_j(t)$，而直接使用 $G_j(t)$ 作为提权依据。该实验用于证明短时提权比长期提权更加稳定，能够避免高收益但长剩余时间任务长期占用高优先级队列。

#### 3.6.3 w/o SLA Bias

去掉推理任务 SLA 压力项，仅根据碎片化收益和网络状态调度。该实验用于验证 SLA 偏移项对保护在线推理任务的必要性。

#### 3.6.4 w/o Interference Cost

去掉网络干扰成本项，不限制提权对其他任务和瓶颈链路的影响。该实验用于证明干扰成本建模可以避免过度提权和队列资源滥用。

#### 3.6.5 Compute-only Frag

碎片化量只考虑 GPU 数量和主机分布，不考虑交换层级、残余带宽和路径延迟。该实验用于证明算网共同碎片化量优于纯计算资源碎片化量。

#### 3.6.6 Network-only Frag

碎片化量只考虑网络带宽和路径延迟，不考虑 GPU 组合和任务资源需求。该实验用于证明仅网络状态也不足以刻画 AI 任务可调度性，算网联合建模是必要的。

最关键的消融实验是 Compute-only Frag 与 Compute-Network Frag 的对比。该实验直接支撑本文第一部分的核心定义。

### 3.8 预期实验结论

实验部分最终应能够支持以下结论。

第一，相比 Fixed Priority 和 Queue-aware Dynamic Priority，本文方法能够显著降低算网共同碎片化量，并提升完整高速互联 GPU 资源块数量。这说明单纯优化队列等待时间并不足以改善集群资源形态。

第二，相比 CRUX-like 方法，本文方法不简单优先占用 GPU 更多的任务，而是优先完成碎片化释放收益更高的任务。因此，本文方法能够释放更多高质量资源块，并提高后续任务可调度成功率。

第三，相比 Frag-routing only，本文方法进一步通过通信侧短时提权改变任务完成顺序，从而改善资源释放轨迹。这说明碎片化优化不应仅发生在路由或任务放置阶段，也应进入运行时通信调度阶段。

第四，在推理 SLA 约束下，本文方法能够维持较低的 SLA violation ratio，同时改善训练任务 JCT 和集群长期可调度性。这说明碎片化收益、SLA 压力和干扰成本的联合建模能够在多目标之间取得可控折中。

第五，消融实验应表明，算网共同碎片化量优于纯计算碎片化量和纯网络状态指标；剩余完成时间归一化、SLA 偏移和干扰成本均对系统稳定性具有必要作用。

### 3.9 当前已完成 full-scale 专家放置实验分析

当前已经完成一组面向 PD 分离推理的 full-scale 对比实验。该实验不是训推混部 CRISP 全量实验，而是验证专家放置、真实 probe 路由、本地 flow 策略和 PD split 组合后，在 MoE 推理通信中的端到端收益。

#### 实验配置

```text
NUM_TASKS = 64
prefill_length in [128, 256]
decode_length in [24, 48]
SUBMIT_INTERVAL = 0.00010
SIMULATION_STOP_TIME = 0.12
PD ratio = 3:1
NEED_PREFILL = 120
NEED_DECODE = 40
EXPERT_NUM = 48
EXPERT_PER_GPU = 8
```

baseline 为所有策略接口全 default：

```text
NEED_PLACEMENT_POLICY default
EXPERT_PLACEMENT_POLICY default
SAME_RANK_ROUTE_POLICY default
LOCAL_FLOW_SCHEDULE_POLICY default
GLOBAL_NEED_UPDATE_POLICY default
PD_SPLIT_POLICY default
```

tuned 策略组为：

```text
EXPERT_PLACEMENT_POLICY domain_balanced_external_min
SAME_RANK_ROUTE_POLICY probe_rtt_delta
LOCAL_FLOW_SCHEDULE_POLICY decode_first_prefill_later
PD_SPLIT_POLICY default
PLACEMENT_PROBE_WEIGHT 0
```

#### 主要结果

| load | method | completed | TTFT ms | TPOT us | avg local queue | P95 local queue |
|---|---|---:|---:|---:|---:|---:|
| light | all-default baseline | 61/64 | 56.376 | 54.515 | 260.2 | 593 |
| light | tuned | 64/64 | 16.006 | 13.339 | 133.8 | 459 |
| medium | all-default baseline | 61/64 | 56.366 | 54.521 | 258.6 | 593 |
| medium | tuned | 64/64 | 16.006 | 13.339 | 134.3 | 459 |
| heavy | all-default baseline | 61/64 | 56.406 | 54.555 | 259.0 | 593 |
| heavy | tuned | 64/64 | 16.006 | 13.339 | 133.8 | 458 |

聚合结果：

- 完成率：baseline 为 `61/64`，tuned 为 `64/64`；
- 平均 TTFT 降低约 `71.6%`；
- 平均 TPOT 降低约 `75.5%`；
- 本地 flow 队列均值降低约 `48.3%`；
- 本地 flow 队列 P95 降低约 `22.7%`。

#### 结果解读

第一，完成率提升说明 tuned 策略改善了高压场景下的资源释放轨迹。baseline 在截止时间内均有 3 个任务未完成，而 tuned 三档负载全部完成。这说明收益不仅体现在已完成任务的平均时延，也体现在可调度性和长尾任务处理能力上。

第二，TTFT/TPOT 大幅下降与本地队列下降高度一致。三档负载中 tuned 的本地队列均值约为 baseline 的一半，P95 队列长度也从约 `593` 下降到约 `458-459`。这表明高压 MoE 推理通信的主要瓶颈来自本地 flow 排队和候选副本路径结构，而调优策略组通过专家放置、probe 路由和 decode-first 本地队列降低了该瓶颈。

第三，专家放置热图和 `prefill/decode_l1_max_load_avg` 显示，48 专家配置下 tuned 策略仍能把 L1 最大频次负载控制在约 `148.1`。这说明当前权重配置能够泛化到比 32 专家更大的专家集合。

第四，tuned 策略的 `expert_slot_utilization`、placement GPU coverage 和 GPU memory utilization 高于 baseline。这是因为 tuned 完成了更多任务并维护了更多有效专家副本。因而在该实验中，`cn_fragmentation_avg` 不应脱离完成率与活跃 placement 数量单独解释为系统状态变差；后续实验应补充“按完成任务数归一化的碎片化时间积分”和“有效可调度成功率”。

第五，tuned 的宿主机 wall time 平均增加约 `52%`。该指标不属于 ns-3 内部时延，不计入 TTFT/TPOT，但说明在线专家放置规划有计算开销。后续应在算法工程化部分加入 plan cache、候选剪枝和状态哈希复用。

第六，最新 probe-aware placement 消融显示，probe 信号应保留在路由层，而不是直接进入专家放置目标。heavy 负载、24 task、PD=3:1、48 专家下，当前最佳版本为：

```text
EXPERT_PLACEMENT_POLICY domain_balanced_external_min
SAME_RANK_ROUTE_POLICY probe_rtt_delta
LOCAL_FLOW_SCHEDULE_POLICY decode_first_prefill_later
PD_SPLIT_POLICY default
PLACEMENT_PROBE_WEIGHT 0
```

其结果为 TTFT `3.437ms`、TPOT `9.638us`。将 probe-cost 加入放置目标后，`PLACEMENT_PROBE_WEIGHT=0.5` 得到 TTFT `3.652ms`，`0.05` 得到 TTFT `3.628ms`，仅作为 tie-break 得到 TTFT `3.630ms`，均弱于当前最佳版本；关闭 route probe 则退化到 TTFT `22.030ms`、TPOT `56.075us`。因此后续主实验应使用当前最佳版本作为 MoE 推理通信子模块默认配置，probe-aware placement 仅作为研究接口保留。

#### 后验访问频次实验

为避免专家放置策略使用初始访问频次 oracle，最新实验把 `EXPERT_ACCESS_FREQ` 改为隐藏真实流量分布，仅用于 alltoall 目的专家采样；放置策略使用：

```text
freq_hat(e, t) = EXPERT_ACCESS_PRIOR + observed_access_count(e, t)
```

每次新 task 下发时刷新后验快照并触发专家放置。本次实验使用 `EXPERT_ACCESS_PRIOR=1.0`、`expert_num=48`、`expert_per_gpu=8`、PD=3:1、32 个任务、`prefill_len=128-256`、`decode_len=24-48`、`submit_interval=0.00016s`。

#### 对后续实验设计的影响

后续实验应将本组结果作为 MoE 推理通信子模块的 baseline evidence，并继续补充：

- 不同 `EXPERT_NUM`：32、48、64；
- 不同 PD ratio：2:1、3:1、4:1；
- 不同 submit interval，用于覆盖轻载到过载；
- plan cache on/off 消融，用于量化调度计算开销；
- 仅 expert placement、仅 route probe、仅 local queue、完整 tuned 的消融对比；
- probe-aware placement on/off 消融，用于验证 probe 是否只应作用于路由层；
- 按完成任务归一化的碎片化时间积分和未来任务可调度成功率。

### 3.10 小结

本文实验设计的核心是从单一网络性能评估扩展到算网共同资源状态评估。传统网络调度实验通常关注 FCT、队列时延或链路利用率，而本文进一步关注任务完成顺序、资源释放轨迹和未来任务可调度性。

通过 ns3-alibaba 调度模块，可以在可控拓扑和混合负载下验证本文方法对运行时碎片化转移的影响。若实验结果能够同时展示更低的 $F_{\text{cn}}(t)$、更多完整高速互联 GPU 资源块、更高未来任务可调度成功率，以及可接受的训练 JCT 和推理 SLA，则能够有力支撑本文的核心主张：通信调度不仅是网络局部优化工具，也可以成为 AI 算力集群运行时碎片化治理的重要控制手段。
